# bms-node

储能电池包的从控节点固件。承担三件事：

1. **采样**：包电压、电流、温度，两级滤波
2. **估算**：SOC（安时积分 + OCV 静置修正）
3. **保护**：四级状态机，过压/欠压/过流/过温/低温，带迟滞与恢复延时

对外通过 CAN 上报数据、通过 UDS 接受诊断与参数写入。
CAN / ISO-TP / UDS 协议栈复用 [can-node](https://github.com/Dik-910/can-node)，
来源与同步方式见 [src/PROTOCOL_STACK.md](src/PROTOCOL_STACK.md)。

## 为什么这个项目值得看

SOC 和保护是 BMS 的两个真问题，也是最容易被做成「能跑但不对」的地方：

| 常见做法 | 问题 | 这里的做法 |
|---|---|---|
| 只做安时积分 | 误差单向累积且不可自愈，跑几天 SOC 就飘了 | 加 OCV 静置修正，但**三个条件同时满足**才允许 |
| 有 OCV 就修正 | 刚充完电端电压虚高，会把 SOC 错误拉到满值 | 电压超出 OCV 表范围直接**拒绝**，不钳位 |
| 阈值单点判断 | 噪声在阈值附近造成继电器高频吸合 | 迟滞带 + 恢复延时，两个都要 |
| 只看滤波值 | 真实快变故障被平滑掉，动作滞后 | 原始值和滤波值**双路同时越限**才动作 |

## 架构

```
        ┌──────────────────────────────────────────┐
        │  bms_node.c  主循环                      │
        │   10ms  采样 → 滤波 → SOC → 保护         │
        │   100ms CAN 上报 0x200                   │

        └───────┬──────────────┬───────────────────┘
                │              │
    ┌───────────▼──────┐  ┌────▼─────────────────┐
    │  bms/  业务层     │  │  can/net/uds 协议栈  │
    │  bms_filter      │  │  （来自 can-node）    │
    │  bms_soc         │  └──────────────────────┘
    │  bms_protect     │

```

业务层不依赖任何平台接口：滤波、SOC、保护都是纯函数，可以单独测试，
也可以原样搬到 STM32（采样源换成 ADC 即可）。

## SOC 估算

### 安时积分

```
SOC = SOC₀ + (1/Q) ∫ I dt        I 充电为正、放电为负
```

> 注：`docs/design.md` 里写的是 `SOC₀ − (1/Q)∫I`，与「充电为正」的定义冲突。
> 以代码为准：充电为正、用加号，与 can-node 的 DBC 一致。

两个实现细节决定精度：

**1. 电荷累积保持 mA·ms 单位，最后才换算。**

若写成 `charge += I * dt / 1000`，每步都有一次整数截断：
50mA × 10ms = 0.5 → 0，跑多久 SOC 都不动。测试
`small current: accumulate then divide` 专门盯这一点。

**2. 从基准点算，不逐次累加。**

```
SOC = SOC₀ + charge_since_anchor · 1000 / (3600000 · Q_mAh)
```

逐次累加每次截断一次，误差单向累积；从基准点算只有一次截断。
OCV 修正时把基准点挪过去、电荷清零。

### OCV 修正

电池静置足够久后端电压趋近开路电压，而 OCV 与 SOC 单调对应。
用此时的 OCV 查表覆盖积分值，把累积误差清零。

触发条件**三者同时满足**（少任何一个都会在某些工况下用不可信的 OCV 覆盖积分值）：

1. 电流绝对值持续低于静置阈值超过 `rest_time_ms`
2. 距上次修正超过 `min_interval_ms`
3. 温度在查表有效范围内

### 一个演示里发现的真问题

跑完整生命周期时发现：过压保护后电压回落到 3423mV，SOC 突然跳到 100%。

原因是最初的 OCV 查表对超范围输入做了**钳位**。3423mV 高于表的顶端 3400mV，
钳位成 100% 意味着「我认为它满电了」——而物理上此时电池刚脱离充电，
端电压还带着表面电荷，根本不是静置 OCV。

**改成超范围返回 −1（不可信，不修正）**，容差只留 20mV（约 4 个采样 LSB）。

这个 bug 单看代码很难发现：钳位看起来是「防御性编程」，实际是把不可信的数据当真值。

### 局限（写在代码里，也写在这里）

- **连续运行时拿不到修正机会**：设备一直在充放电，静置时间永远不够，误差持续累积。
  测试 `drift when correction never happens` 量化了这一点：50mA 的传感器零点漂移，
  24 小时累积 1.2% 偏差，且不可自愈。
- **OCV 表精度受老化影响**：容量衰减后 `Q_rated` 需要随 SOH 更新，本版本不实现 SOH。
- **LFP 平台期**：3.25–3.32V 覆盖 30%–70% 容量，电压只变 70mV。
  采样精度 ±5mV 就意味着 ±4% 的 SOC 误差，所以这段区间更依赖积分而不是查表。

## 保护状态机

```
正常 ──告警──> 告警 ──全部回到阈值−迟滞──> 正常
  │              │
  └──保护────────┴──> 保护 ──全部回到阈值−迟滞──> 恢复 ──稳定 T 秒且无告警──> 正常
                                                      └──再次越限──> 保护（计时清零）
```

三个设计点：

**1. 迟滞**：阈值附近有采样噪声，没有迟滞带会造成状态高频翻转——继电器反复吸合、故障码疯狂刷写。迟滞宽度取噪声峰峰值的 2 倍。

**2. 恢复延时**：保护后立刻恢复，若故障仍存在就变成「断开—恢复—再断开」，对接触器寿命伤害很大。

**3. 双路判断**：只看滤波值会被平滑掉真实快变故障，只看原始值会被单次毛刺误跳闸。**两者同时越限**才动作。

双路只用于**进入**判断。退出用滤波值 + 迟滞，否则毛刺会让保护状态反复退出又进入。

恢复的条件是「延时到」**且**「无告警」——只看延时的话，带着告警合闸会立刻又跳。

## 采样与滤波

```
x -> [滑动平均 8 点] -> [一阶低通 α=0.2] -> y
```

两级串联的原因：滑动平均压白噪声但对阶跃响应慢，一阶低通压高频毛刺但对缓慢漂移无能为力。

三个容易写错的点：

- **滑动平均窗口未满时**按已有样本数平均，不能拿 0 充数
- **低通首值直接采用**，否则开机后一段时间的滤波值是「从零爬上来」的假数据
- **低通必须四舍五入**：直接截断会产生稳态误差，α=0.2、输入 20000 时输出会卡在 19996
  再也上不去（整数不动点）。这个误差会被保护判断当成真实偏差

坐标基准：电压 mV、电流 mA、温度 0.1℃、SOC 0.1% —— 全部定点，不用浮点。
目标芯片可能是没有 FPU 的 Cortex-M0/M3。

## CAN 上报

`0x200` PackData，100ms 周期，字段定义见 can-node 的 `docs/can_matrix.dbc`：

```
candump 实测：  vcan0  200   [8]  C2 10 00 00 50 41 00 00
                     电压 42.90V  电流 0A  SOC 80%  温度 25℃
```

用的是 DBC 生成的 `can_matrix_pack_data_pack()`，不是手写字节偏移——
协议改了重新生成即可，节点代码不用动。

## UDS 诊断

| DID | 内容 | 会话 | 需解锁 |
|---|---|---|---|
| `0xF190` | VIN（17 字节，走多帧） | 默认 | 否 |
| `0x0101` | 包电压 | 默认 | 否 |
| `0x0102` | 电流（int32，大端） | 默认 | 否 |
| `0x0103` | 温度 | 默认 | 否 |
| `0x0104` | SOC（千分比） | 默认 | 否 |
| `0x0105` | 保护状态 | 默认 | 否 |
| `0x0106` | 故障位（16 位掩码） | 默认 | 否 |
| `0x0201` | 过压保护阈值 | 扩展 | **是** |

`0x0201` 写入做了范围校验（40–50V）：写坏阈值比不写更危险。
本版本只改内存，掉电丢失——参数持久化需要 Flash 参数区，未实现。

## 构建与运行

```bash
make                # 编译 node 与全部测试
make test           # 87 项断言
./node --if vcan0   # 在 vcan0 上跑 30 秒完整生命周期
```

需要先有 vcan：

```bash
sudo modprobe vcan && sudo ip link add dev vcan0 type vcan && sudo ip link set up vcan0
```

`make test` 共 87 项：

| 套件 | 覆盖 |
|---|---|
| `bms_filter_test` | 15 项：窗口未满、稳态无偏、阶跃单调、噪声抑制 |
| `bms_soc_test` | 27 项：积分精度、钳位、OCV 修正三个门槛、无修正时的漂移 |
| `bms_protect_test` | 43 项：四条迁移路径、迟滞、双路、过流分方向、温度上下限、告警阻塞恢复 |

## 演示输出

采样由一段场景脚本驱动（真实硬件上换成 ADC，其余不变）：

```
[bms] initial soc=800 permille (will be corrected by OCV)
[bms] t=    0ms  state -1 -> 0  faults=0x0000 relay=CLOSED
[bms] t= 3002ms  42900mV      0mA  25.0C  soc=500  prot=0 faults=0x0000 corr=1   ← OCV 修正
[bms] t= 5004ms  43198mV  14998mA  25.8C  soc=500  prot=0 faults=0x0000 corr=1   ← 充电
[bms] t= 8139ms  state 0 -> 1  faults=0x0001 relay=CLOSED                        ← 过压告警
[bms] t=11093ms  state 1 -> 2  faults=0x0101 relay=OPEN                          ← 过压保护
[bms] t=13047ms  state 2 -> 3  faults=0x0001 relay=OPEN                          ← 回落，恢复中
[bms] t=23049ms  state 3 -> 0  faults=0x0000 relay=CLOSED                        ← 恢复完成
[bms] final: soc=500 permille, state=0, faults=0x0000, trips=1, corrections=3
```

继电器只在 PROTECT 与 RECOVER 期间断开——恢复确认期间仍然断开，
这是「延时确认」的意义：确认稳了才合闸。

## 已知限制

- **采样源是场景脚本**，不是真实 ADC。硬件到位后替换 `scene_sample()` 即可，其余不动
- **参数不持久化**：`0x2E` 写入的阈值掉电丢失
- **无 SOH 估算**：`Q_rated` 固定，老化后 SOC 会偏
- **单体电压未采集**：目前只有包级电压，单体均衡与单体过压保护需要专用采样芯片（如 BQ769x0）
- **无看门狗**：目标板需要独立看门狗 + 主循环喂狗
- **Bootloader 未接入**：can-node 有双区 Bootloader，本节点尚未对接
